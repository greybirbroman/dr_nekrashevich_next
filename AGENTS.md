# Проект

Компоненты по умолчанию серверные. 'use client' добавляй на минимальной
границе, требующей состояния, эффектов, браузерных API или клиентской библиотеки.
По возможности получай и преобразуй данные на сервере; избегай цепочек
зависимых клиентских запросов и лишних данных в передаваемых клиенту props.
Сохраняй соглашения маршрутов, metadata, error/loading, CSS modules и алиасы.
Добавление и обновление зависимостей требуют согласования в задаче;
установка OpenSpec по инструкции ниже разрешена отдельно.

Прямые указания пользователя и правила проекта имеют приоритет над навыками.
Уже разрешённые действия выполняй без повторного согласования. Если навык
требует остановки, укажи файл и конкретное требование.

Проверяй точную версию Next/React при использовании зависящего от неё API.
Для Next доступна документация установленного пакета в
node_modules/next/dist/docs/.

## OpenSpec обязателен для изменений поведения

`openspec/` — источник истины для планируемого поведения приложения.
Перед изменением функциональности, API, схемы контента, контракта работы
приложения или поведения CI создай или обнови соответствующее изменение
OpenSpec и прочитай его `proposal`, `specs`, `design` и `tasks`.

Если пакет OpenSpec не установлен локально, установи его в этом репозитории:

```powershell
npm install --save-dev @fission-ai/openspec
```

Если проект ещё не инициализирован для OpenSpec или отсутствует интеграция
нужного агента, выполни:

```powershell
npx openspec init --tools 'codex'
```

Если локальный CLI недоступен как openspec, вызывай его через
npx --no-install openspec, используя аргументы из интеграции.

Используй созданную при инициализации интеграцию для своего агента:

- Codex: `$openspec-propose "<описание изменения>"`

После propose представь артефакты; если пользователь уже поручил реализацию,
после показа артефактов переходи к apply; если он запросил только подготовку OpenSpec,
остановись после proposal.
Храни `openspec/` в системе контроля версий. Архивируй изменение только после
выполнения его задач и проверок. Пользователь может явно отменить этот порядок
для отдельной узкой задачи.

OpenSpec задаёт этапы изменения. При использовании Superpowers сохраняй
дизайн и план в тех же openspec/changes/<change>/design.md и tasks.md.
Применяй его методы внутри этих этапов, без отдельного цикла планирования
и согласований. Пересматривай артефакты только при новых требованиях или данных.

## Проверки

Проверяй затронутое поведение и запускай применимые проверки.
Изменения, влияющие на результат production-сборки, проверяй через build.

При изменении интерактивности проверь границы server/client, hydration
и затронутый сценарий в браузере. Используй Chrome DevTools MCP или
Playwright MCP; при необходимости найди нужные команды через поиск
инструментов среды. Computer Use не используй.

Сообщай результаты и незапущенные проверки. Если оба браузерных MCP
недоступны, явно укажи, что браузерная проверка не выполнена.

Новые тесты и необходимые scripts добавляй по запросу пользователя
или для проверки значимого поведения и защиты от регрессий.
Для текстовых, форматных и других правок без изменения поведения
новые тесты без запроса не добавляй. Объём проверок выбирай
соразмерно риску изменения; используй существующую тестовую инфраструктуру,
если её достаточно. Успешные проверки повторяй или расширяй
только при новых основаниях.
